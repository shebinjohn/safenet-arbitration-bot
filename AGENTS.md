# Safenet Arbitration Bot

This bot helps the Safenet Security Council arbitrate disputed Safenet transactions. When sentinels split on a transaction, the `SentinelOracle` request is `FROZEN` and the Council must rule `secure` or `insecure` (or decide it is `out of scope`) under the Safenet Arbitration Charter, considering only the rules that the sentinels reported (see [Disputed rules](#disputed-rules)). The bot collects the evidence, runs deterministic Charter checks in code, falls back to an LLM for ambiguous cases, and drafts a ruling for humans to review. It also keeps a text corpus of past rulings that it uses as precedent.

> The repository is greenfield. This file describes the target architecture. Keep it up to date as components land, and replace "planned" wording with what actually exists.

## Protocol Background

### Sentinel oracle

- **Proposal.** A Safe transaction is proposed via `Consensus.proposeTransaction(oracle, oracleData, transaction)`. This emits `TransactionProposed(safeTxHash, safeId, oracle, epoch, oracleData, transaction)` and calls `SentinelOracle.postRequest`. The `transaction` is a `SafeTransaction` struct: `chainId, safe, to, value, data, operation, safeTxGas, baseGas, gasPrice, gasToken, refundReceiver, nonce`.
- **Request ID → transaction.** The oracle `requestId` is the Consensus `transactionProposal` message hash, `domainSeparator().transactionProposal(epoch, oracle, keccak256(oracleData), safeTxHash)`. `SentinelOracle` does not store the transaction. To find it, compute the proposal block as `getRequest(id).terms.commitDeadline - COMMIT_WINDOW`. Then take the `TransactionProposed` logs from `Consensus` in that block and pick the one whose recomputed message hash equals `requestId`.
- **Request lifecycle.** Sentinels bond and `commit`, then `reveal(requestId, approve, salt, reason)`. `finalize` settles the request:
  - a unanimous vote resolves it directly to `RESOLVED_APPROVED` or `RESOLVED_DENIED`;
  - no revealed votes time it out (`TIMED_OUT`, `RequestTimedOut`);
  - a split vote moves it to `FROZEN` and emits `DisputeTriggered(requestId, deadline)`. A dispute is only arbitrated in this `FROZEN` state.
- **Arbitration outcomes.** From `FROZEN`, the arbitrator (the Council's Arbitrator Safe) takes one of three paths:
  - `resolveDispute(requestId, approveWins, context)`, emitting `DisputeResolved(requestId, outcome, slashed, context)`. `approveWins = true` is a `secure` ruling and `false` is `insecure`. The losing side's sentinels are slashed.
  - `markOutOfScope(requestId, context)`, emitting `DisputeOutOfScope`.
  - No action. `timeoutArbitration` becomes callable after `deadline`, emitting `ArbitrationTimedOut`.

  Out of scope and timeout have the same economic effect: fees are refunded and bonds are returned in full. `context` is either the ruling text itself or an IPFS CID pointing to it.

- **Sentinel votes.** Each revealed vote carries a `reason` string that the protocol does not validate. By convention, `secure` votes have an empty reason and `insecure` votes cite the rules that the transaction fails, as a comma-separated list of rule identifiers such as `R-4.1, R-4.2` (§ 2.14). These reasons decide which rules a dispute is arbitrated under (see [Disputed rules](#disputed-rules)).
- **Two chains.** `Consensus` and `SentinelOracle` run on Gnosis Chain (chain ID 100). The disputed Safe can be on any network the Charter covers. Read the Safe's state (codehash, owners, modules, transfer history) on the Safe's own chain, at the last block before the proposal time. Evidence must not include effects of the transaction itself or anything that happened later (§ 2.8, § 3.6).
- **Deployments.** `arbot` defaults to the oracle-backed `SentinelOracle` and `Consensus` deployment on Gnosis Chain, whose addresses are in `internal/safenet/addresses.go`. This is the latest testnet deployment, whose contracts match the current Safenet sources: its `NewRequest` event has a DAO fee share, and revealing the last committed vote finalizes a request. Its `ARBITRATION_TIMEOUT` is 50,400 blocks and its `COMMIT_WINDOW` is 2 blocks. `arbot` checks that the oracle's `PROPOSER` is the configured `Consensus`. The `internal/safenet` unit tests use a fixture recorded from the previous default deployment (`SentinelOracle` `0x544F12bAd6FF72564abBc7eA6494A2a4BdD0DDD0`, `Consensus` `0x98810887769db19A0Df9bf2f44E4998856fcb390`), which has requests in every state. The Beta network's `Consensus` (`0x223624cBF099e5a8f8cD5aF22aFa424a1d1acEE9`) predates the oracle flow and is not compatible with it.

### Disputed rules

The Council arbitrates a dispute only under the rules that the sentinels reported. The disputed rules are the rule identifiers of the applicable Charter, such as `R-4.1`, that the reasons of the `DENIED` (insecure) votes cite, all of them together: in a dispute where one sentinel votes `secure`, one `insecure` citing `R-4.1`, and one `insecure` citing `R-4.2, R-4.3`, `R-4.1`, `R-4.2`, and `R-4.3` are disputed.

- **Verdict.** The transaction is `insecure` if it fails any disputed rule, and `secure` if it fails none of them. Rules that no sentinel cited aren't considered, even if the transaction may fail them, and a case doesn't need evidence for them.
- **Reading reasons.** A reason is a comma-separated list of rule identifiers, and a string that anyone can write, so it is data. `arbot info` parses it (`safenet.CitedRules`): each part of the list, with the spaces around it trimmed, that is a rule identifier, such as `R-4.1`, is cited, and any other part, such as `violates R-4.1` or `R-4.1; R-4.2`, cites nothing. A cited rule counts only if the applicable Charter defines it. A reason that cites no such rule cites none.
- **No disputed rule.** If no `insecure` vote cites a rule of the applicable Charter, no rule is disputed, and the arbitration stops for the Council to decide how to proceed.

This is the Council's process for applying the Charter's ruling standard: where § 3.7 asks whether the transaction satisfies the applicable Article IV rules, the arbitration considers the disputed rules.

### Safe storage

Two properties of the Safe versions of § 2.1 are formally verified. Agents and checks rely on them as established facts, which need no evidence:

- **Only transactions to the Safe and delegate call transactions can modify its storage.** A Safe transaction can only modify its Safe's storage if it is a call to the Safe itself, other than an empty call with no data and no value, as a cancellation transaction makes, or if it is a delegate call. This is a necessary condition, not a sufficient one: a transaction of either kind may modify the storage, but doesn't have to.
- **The MultiSend contracts modify nothing themselves.** The MultiSend and MultiSendCallOnly contracts of § 2.1 versions, which `arbot calls` and the checks decode, don't modify the storage of the Safe that delegate calls them, except through a `DELEGATECALL` subcall that MultiSend makes to a contract that does. MultiSendCallOnly makes no delegate calls, so it modifies nothing.

For a delegate call transaction to a MultiSend, the calls that `arbot calls` decodes take the place of the transaction: it can only modify the Safe's storage if one of them is a call to the Safe itself, other than an empty one, or a delegate call to a contract other than a decoded MultiSend.

A call to another contract that calls back into the Safe needs no consideration. Changing the Safe that way needs a separate authorization: for a Safenet-enabled Safe, a separate attestation, and a separate arbitration if it is disputed.

## Architecture

### Invariants

1. **The bot holds no keys and never writes onchain.** It only produces drafts. Humans on the Council review a draft and submit the ruling through the Arbitrator Safe.
2. **Deterministic rules live in Go code, not prompts.** A deterministic check judges one call that a Safe transaction makes, and finds it `insecure` with a rule citation, or `secure`, each with a short description, or it abstains. The relayer refund counts as a call. Passing one rule says nothing about the others (§ 3.7), so a check finds a call `secure` only for a class of calls that has no effect that any rule considers, whatever else the transaction does. For example, a delegate call to MultiSend with no transactions. A transaction is `secure` only if every call it makes is. A check that only shows that its own rule is not broken must abstain. Every other `secure` outcome comes from the LLM stage.
3. **LLM output is always a draft.** It must cite rules, name the precedents it applied or distinguished, and meet the ruling-explanation requirements of § 5.2: Safe and network, Charter version, rule IDs, material evidence, and the reason. Only admissible evidence may be used (§ 3.3–3.5).
4. **Sane defaults, no required configuration.** RPC URLs come from <https://chainlist.org/rpcs.json>. IPFS content (Charter versions, `context` CIDs) is fetched through public gateways. Overrides may exist, but no command may require them. Overrides go in an optional JSON configuration file, loaded by `internal/config` from `--config`, `./arbot.config.json`, or `$XDG_CONFIG_HOME/arbot/config.json`, in that order. A missing file means the defaults apply. Current settings are `rpcs` (chain ID to RPC URL, e.g. `{"1": "https://..."}`), `ipfs` (gateway base URL), `txServices` (chain ID to the base URL of the Safe Transaction Service, e.g. `{"1": "https://api.safe.global/tx-service/eth"}`, where an empty URL leaves the service out, and which defaults to Safe's public service for each network that the Charter covers), and `oracle` and `consensus` (the Gnosis Chain `SentinelOracle` and `Consensus` addresses, defaulting to the deployments above).
5. **Go standard library only, as far as reasonably possible.** Do not add third-party modules for things the standard library makes easy to write. For example, write the Ethereum JSON-RPC client, ABI encoding and decoding, and IPFS/ENS lookups by hand on top of `net/http` and `encoding/json` rather than pulling in `go-ethereum`. A dependency is only justified for something that is impractical or risky to reimplement. Keccak-256 is one such case: the standard library's `crypto/sha3` does not provide it. Even then, prefer `golang.org/x/...` modules and keep them few. The JSON-RPC client is `internal/ethrpc`, whose `ScanLogs` splits `eth_getLogs` into block ranges that public RPCs accept, and ABI encoding and decoding is `internal/solabi`. The clients of public services (RPC nodes, IPFS gateways, the Safe Transaction Service, and the lists of RPCs and gateways) send their requests with `httpretry.Client`, which retries a request that is rate limited with `429 Too Many Requests`, or that a gateway rejects with `502 Bad Gateway`, `503 Service Unavailable`, or `504 Gateway Timeout`, with exponential backoff or after the response's `Retry-After`, up to 4 times. The clients only read, so a request can be sent again.

### Components (planned)

- **`cmd/arbot`**: the single top-level Go CLI. Every capability lives here as a subcommand: fetching a request and its transaction, resolving the applicable Charter, reading a Safe's history, verifying that an account is an official Safe (codehash of a § 2.1 version at a given block), running deterministic checks, and indexing and linting the corpus. Put logic in `internal/` packages and keep `cmd/` thin. The subcommands live in `internal/cli`, and `cmd/arbot` only calls `cli.Run`, so the end-to-end tests run the CLI in-process and Go's test cache reruns them when it changes. Implemented so far:
  - `arbot charter [-block N | -request-file <path>] [-verify <file>]` resolves `charter.safenet-gov.eth` on Ethereum Mainnet and prints the Charter fetched from IPFS. With `-request-file`, it reads a request that `arbot info -json` wrote, and fetches the Charter that the request's `charter` name references at its `ethereumBlock`. With `-verify`, it doesn't fetch the Charter: it checks that the IPFS CID of the file is the one that the name references at the block, and prints the CID, or fails if they differ.
  - `arbot pending [-json]` lists the `FROZEN` requests awaiting arbitration as of the latest Gnosis Chain block, with their frozen block and deadline. It scans the last `ARBITRATION_TIMEOUT` blocks of oracle logs.
  - `arbot info [-json] <request-id>` shows a request, as of the latest Gnosis Chain block: its terms, its proposal and Safe transaction, the sentinel votes and reasons, the rules that each `DENIED` vote's reason cites and all of them together, the [disputed rules](#disputed-rules), and its arbitration, if any. With `-json`, each vote has its `rules`, empty for a vote that isn't `DENIED`, and the request has its `disputedRules`, in the order of their first citation. The rules are parsed from the reasons alone, so some may not be rules that the applicable Charter defines. The proposal includes the last blocks before its time on Ethereum Mainnet and on the Safe's chain (`ethereumBlock` and `safeBlock`), found with `ethrpc`'s `SearchBlock`. Read the Safe's state at `safeBlock`, and fetch the Charter with `arbot charter -request-file`.
  - `arbot classify [-json] <request-id>` runs the deterministic checks on a request and prints its verdict: `unclassified`, or the classification that decided it, `secure  <description>`, or `insecure  <rule>  <description>`. A `secure` description joins those of the checks that matched each call with `; `. With `-json`, it writes `{"verdict": null | "secure" | "insecure", "rule": "...", "description": "..."}`, leaving out an empty rule or description. With `-request-file <path>` in place of the request ID, it classifies the request that `arbot info -json` wrote to the file, without fetching it, though the checks still read the Safe's chain. With `-list` in place of the request ID, it lists the classification of every check, in the order that they run, as a table with a verdict, rule (`-` if none), and description column, or with `-json`, as an array of classifications.
  - `arbot calls [-json] -request-file <path>` lists the calls that the Safe of a request that `arbot info -json` wrote makes, as `arbot classify` judges them, read from the Safe's chain as of its `safeBlock`: delegate calls to the MultiSend and MultiSendCallOnly contracts of § 2.1 versions decoded into the calls that they make, a root call that reverts whatever the state or makes no calls replaced by a `reverting` or `empty` placeholder, and a last `refund` call that pays the largest gas refund that the transaction allows, if any. It shows the Safe's code hash and the § 2.1 proxy version whose official proxy factory deploys a proxy with that code on its network, and its singleton, in storage slot 0, with its § 2.1 singleton version, each if any. Each account that the Safe calls has its code hash and size, whether it is the Safe itself, and the contract of a § 2.1 version that it is (MultiSend, MultiSendCallOnly, or the Safe or SafeL2 singleton), identified by its address on the networks that the Charter covers if it has code. It prints the Safe, the target of the Safe transaction's own call, and a table of the calls with long data shortened, or with `-json`, `{"chainId", "safeBlock", "safe": {"address", "codeHash", "codeSize", "proxyVersion", "singleton", "singletonVersion"}, "target": <account>, "calls": [{"kind": "root" | "batched" | "refund", "placeholder", "to": <account>, "value", "operation", "data"}]}`, where an account is `{"address", "codeHash", "codeSize", "self", "contract": null | {"name", "version"}}`, the versions are null if there is none, and `placeholder` is left out of a call that isn't one. The logic is `checks.Calls`, which shares the decoding of the checks.
  - `arbot safe [-json] -request-file <path>` shows the settings of the Safe of a request that `arbot info -json` wrote, as § 2.10 lists them, read from the Safe's storage on its chain as of its `safeBlock` with the storage layout of the § 2.1 Safe versions (`internal/safesettings`), rather than by calling the singleton's code: its singleton, owners, threshold, nonce, enabled modules, fallback handler, guard, and module guard, which only Safe 1.5.0 has. The settings are meaningless for an account that isn't a Safe of a § 2.1 version, which `arbot calls` shows, and the zero address means that a setting isn't set. It fails if a list of owners or modules doesn't end where it started. It prints the settings and the lists, or with `-json`, `{"safe", "chainId", "safeBlock", "singleton", "owners", "ownerCount", "threshold", "nonce", "modules", "fallbackHandler", "guard", "moduleGuard"}`, where the lists are in the order that the Safe links them, and `ownerCount` is the count that the Safe stores apart from its list.
  - `arbot transfers [-json] [-to <address>] [-blocks N] -request-file <path>` lists the ERC-20 transfers out of the Safe of a request that `arbot info -json` wrote, read from the Safe's chain as of its `safeBlock`: the `Transfer` events of any token that has the Safe as sender, in the last `-blocks` blocks up to `safeBlock` (default 100,000), or only those to `-to`. It scans that range only, and reports it, so a transfer before it isn't listed. The events show that a token moved, not why: an account with an allowance can move tokens out of the Safe without it making a transaction. Native and ERC-721 transfers aren't listed. It prints a table of block, transaction, token, recipient, and value in the token's smallest unit, or with `-json`, `{"safe", "chainId", "fromBlock", "toBlock", "to", "transfers": [{"type": "erc20", "block", "txHash", "logIndex", "token", "from", "to", "value"}]}`, where `to` is left out unless `-to` is set, and `type` says what moved so that other kinds can be added.
  - `arbot executions [-json] [-blocks N] -request-file <path>` lists the Safe transactions that the Safe of a request executed, read from the Safe's chain as of its `safeBlock`: the `ExecutionSuccess` and `ExecutionFailure` events of the Safe in the last `-blocks` blocks up to `safeBlock` (default 100,000). It scans that range only, and reports it, so an execution before it isn't listed. Executions by modules aren't listed. The events only have the hash of each Safe transaction, so it decodes the transaction from the first source that has one with that hash, and reports the source: `event` (the `SafeMultiSigTransaction` event of SafeL2), `calldata` (of the onchain transaction, if it calls `execTransaction` on the Safe), `trace` (of the onchain transaction, with `debug_traceTransaction` and the `callTracer`, for the calls to `execTransaction` that it makes, which needs a node that serves it), and `service` (the Safe Transaction Service, an offchain source). It reports a transaction only if its EIP-712 hash is the one that the Safe logged, so no source can misreport what was executed. The calldata and traces have no nonce, so it is worked out from the Safe's nonce at `safeBlock`, since every execution uses one. If no source has the transaction, it is an unknown transaction. It prints a table of block, onchain transaction, result, Safe transaction hash, and source, nonce, target, value, operation, and the selector and length of the data of each, or with `-json`, `{"safe", "chainId", "fromBlock", "toBlock", "executions": [{"block", "txHash", "logIndex", "safeTxHash", "success", "payment", "source", "transaction"}]}`, where `transaction` is the Safe transaction with all of its fields and data, or `null` and no `source` if it is unknown.
  - `arbot events [-json] -request-file <path> <transaction-hash>` lists the events that a transaction logged, read from the Safe's chain of a request that `arbot info -json` wrote, as of its `safeBlock`. It fails for a transaction in a later block, since its events aren't evidence of the proposal. Each log has its emitter, topics, and data, and, if it is a well-known event of an ERC-20 or ERC-721 token, WETH, or a Safe 1.3.0, 1.4.1, or 1.5.0 (`internal/events`), its name, signature, and arguments. Logs are decoded by their signature only, and any contract can emit a log with the signature of a well-known event, so the emitter matters. A transaction that reverted has no events. It prints the transaction's block, status, sender, and target, then each log, with data over 36 bytes shortened, or with `-json`, `{"chainId", "safeBlock", "txHash", "block", "status": "success" | "reverted", "from", "to", "events": [{"logIndex", "emitter", "topics", "data", "event": null | {"name", "signature", "args": [{"name", "type", "value"}]}}]}`, where `to` is null for a contract creation.
  - `arbot index [-w] [-corpus <dir>] [-block N]` indexes the arbitrator's rulings into the [rulings corpus](#rulings-corpus) in `<dir>` (default `corpus`): the requests with a `DisputeResolved` or `DisputeOutOfScope` event of the oracle after the block in the corpus's `index.json`, up to `-block` (default: the latest finalized Gnosis Chain block). It writes a corpus file for each, and moves the index to `-block`. It reads the requests as of the latest block, which gives the same requests as reading them at `-block`, since a ruling settles a request for good, so its output depends only on the blocks up to `-block` and the corpus. Without `-w`, it prints the corpus files and the index that it would write, each after a `==> <path> <==` line. With `-w`, it writes them, the index last. It keeps a corpus file that already exists with the same content, and fails if one exists with other content, before it writes anything.
  - `arbot tags [-json] [-corpus <dir>] <request-id>` lists the tags of the ruling on a request in the corpus in `<dir>` (default `corpus`): the `key: value` lines of the file's header, then, after an empty line, those of the header that its ruling document starts with, if it has one (see [Rulings Corpus](#rulings-corpus)). With `-json`, it writes `{"header": {...}, "document": {...}}`, each an object of tags by key.

  Flags must come before a request ID.

- **Deterministic checks**: one Go check per class of calls that the Charter decides, each with its verdict, the rule ID for `insecure`, and a short description. Checks live in `internal/checks` and are listed in its `checks` variable, grouped by verdict in the order that they run. A check judges one call at a time, given the Safe's address and chain ID, and an `env` from which it can read the Safe's chain at `safeBlock`. The calls are those that the Safe makes, with delegate calls to the MultiSend and MultiSendCallOnly contracts of § 2.1 versions decoded into the calls that they make, followed by a synthetic call that pays the largest relayer refund the transaction allows. Each call's `kind` is `Root`, `Batched`, or `Refund`, for the Safe transaction's own call, a call of a MultiSend, and the refund. A call that reverts whatever the state, such as a call to MultiSend that isn't a delegate call, is replaced by a placeholder from `revertingMultiSend`: a call with no data to the MultiSend that the Safe transaction calls. The transaction still pays its refund after a reverting call. A MultiSend that makes no calls is replaced by one from `emptyMultiSend`: a delegate call to its `multiSend` with no transactions. A transaction therefore always makes at least one call. There are no `out-of-scope` checks: R-4.0 applies to every transaction, on any network, so every transaction is in the scope of Article I (§ 3.9). `arbot classify` runs the `insecure` checks on every call: first `offNetwork` for a Safe on a network that Article I doesn't list, and `unsupportedSafe` for an account that isn't a Safe under § 2.1, both under R-4.0, then others such as one for each Safe function that changes a setting under R-4.1. It returns the classification of the first check that matches a call. Otherwise, the request is `secure` if a `secure` check matches every call, and `unclassified` if not. `arbot classify -list` lists the checks. `arbot classify` runs every check, whatever the [disputed rules](#disputed-rules) are, so the `arbitrate` skill uses an `insecure` classification only if its rule is disputed, and a `secure` one, which holds under every rule, as it is. Add a check only for cases the Charter makes unambiguous. For example, R-4.1 makes a settings change such as `addOwnerWithThreshold` insecure unless it matches an allowed exception. Use the `add-check` skill (`skills/add-check/SKILL.md`) to add one.
- **Agent layer**: `claude` and `codex` for now. Agents get their data by shelling out to `arbot`. The facts that `arbot` reports are correct, including the identifications that it makes, such as the § 2.1 proxy and singleton versions of a Safe that `arbot calls` reports, which it makes by verifying the Safe's code hash and singleton address against the official deployments of that version on the Safe's network. Agents take them as established, and don't ask how `arbot` made them, read its source code to explain them, or record its internals as gaps: a wrong fact is a bug in `arbot`, to fix in `arbot`, not a question for an arbitration. They must not reimplement chain reads or checks in ad-hoc scripts, such as with `cast` or `curl`. When `arbot` can't provide some evidence, they report it as a gap, and the `add-evidence` skill adds the command that provides it, so that an arbitration can be done with `arbot` alone. Agent skills live in `skills/<name>/SKILL.md`, with `.claude/skills` and `.codex/skills` symlinked to that directory. The `add-check` skill adds a deterministic check, `add-evidence` adds an `arbot` command that gathers evidence, `add-subagent` adds a sub-agent, and `arbitrate` drafts a ruling for a request under its [disputed rules](#disputed-rules): it classifies the request with `arbot classify`, and if the checks don't decide the disputed rules, runs the sub-agents to build and review a case under them, then fills in the template `skills/arbitrate/report.md` in `.msgboard/<first 12 characters of the request ID>/`. Sub-agents are described under [Agents](#agents).
- **Future direction**: using a general-purpose coding agent is a stopgap. The plan is to move to a purpose-built arbitration agent (for example, on Google's ADK) with a narrow toolset backed by the same `arbot` commands. Build tooling so that move is easy: stable CLI output (JSON where machines consume it) and no dependence on one agent's quirks.

### GitHub workflows

- **Arbitrate** (planned, `workflow_dispatch`, input `request_id`): fetches the request, then runs the deterministic checks. If a check fails, it drafts the ruling from that failure. Otherwise it runs the agent with the relevant corpus precedents. It then opens an issue with the classification and the draft ruling for Council review.
- **Index** (`.github/workflows/index.yml`, hourly `cron` and `workflow_dispatch`): runs `arbot index -w`, and on `main`, commits the new corpus files and index and pushes them, with the `CORPUS_BOT_SSH_KEY` deploy key of the `corpus-index-main` environment. On other branches, it indexes without committing, to test the workflow.
- **Configure** (`.github/actions/configure`): a composite action for workflows that run `arbot`. It writes a configuration file with the RPC URLs of Ethereum Mainnet (an archive node), Gnosis Chain, and Arbitrum One, and the IPFS gateway URL, that it is given, leaving out those that are empty, and outputs its path for `arbot -config`. Workflows pass it the `MAINNET_RPC_URL`, `GNOSIS_RPC_URL`, `ARBITRUM_RPC_URL`, and `IPFS_GATEWAY_URL` secrets, since public RPCs and gateways rate limit runs, and work without them.

## Rulings Corpus

`corpus/` holds one Markdown file per onchain-recorded arbitration outcome, named `corpus/<requestId>.md`. Every file starts with a header that has **exactly 10 lines**. Agents can therefore scan all past cases with `head -n 10 corpus/*.md`, list the tags of a case with `arbot tags <request-id>`, and then read in full only the cases that look relevant.

```
---
request: 0x<requestId>
outcome: secure | insecure | out-of-scope
rules: R-4.1, R-4.5            (or -)
chain: <Safe chain ID>
safe: 0x<Safe address>
charter: <IPFS CID of applicable Charter version>
proposed: <ISO-8601 UTC proposal time>
record: 0x<Gnosis Chain tx hash of resolveDispute/markOutOfScope>
---
```

Rules for the header:

- Every key is always present, in this order, on a single line. Use `-` when a field is empty.
- Headers are generated by `arbot index`, not written by hand. It fills in `rules` with the rule IDs, such as `R-4.1`, that the ruling document cites, in the order they are first cited.
- If the header format changes, change the line count here, in the tool, and in the skills and agents together.

The body follows the header: the proposal, the decoded Safe transaction, the sentinel votes and reasons, and the ruling. Then a `<!-- DOCUMENT START -->` line and a `---` line, followed by an empty line, start the ruling document: the IPFS document that the ruling's `context` references, or the `context` itself if it is the ruling text. Everything after them is the document, verbatim. Prettier ignores `corpus/`, since its files must stay as `arbot index` writes them.

The ruling document may start with a header of its own, delimited by `---` lines like the file's header, with one `key: value` tag per line, such as:

```
---
precedents: <comma-separated request IDs applied or distinguished, or ->
tags: <comma-separated kebab-case fact-pattern keywords>
summary: <one line describing the fact pattern and holding>
---
```

The Council writes these tags in the ruling, so they are only as accurate as the ruling. `arbot tags` lists them after the file's header tags. A document whose header is malformed, such as one with a YAML list, has no tags.

`corpus/index.json` is `{"block": N}`, where `N` is the last Gnosis Chain block whose rulings are in the corpus. The corpus starts at the block of Wednesday, October 14, 2026, 00:00:00 UTC (48,743,477), so the empty corpus has the block before it.

## Sub-agents

Each sub-agent's instructions live in `agents/<name>.md`, shared by both CLIs. Stubs in `.claude/agents/<name>.md` and `.codex/agents/<name>.toml` register them with Claude Code and Codex CLI, set the model, and point to the shared instructions. Use the `add-subagent` skill (`skills/add-subagent/SKILL.md`) to add or change one.

- `charter-summarizer`: summarizes a fetched Charter, preserving rule identifiers, exceptions, and section citations.
- `detective`: collects the evidence for a request with `arbot` commands, for its disputed rules, given the request that `arbot info -json` wrote, the disputed rules, and the Charter summary, and writes a report of the facts, each with its source and the rules it bears on, and of the gaps that `arbot` can't fill yet. It only collects evidence, and leaves the verdict to `prosecutor`. Orchestrators run it after `charter-summarizer` for a request that `arbot classify` leaves `unclassified`, before drafting a ruling, and use its gaps to decide which `arbot` commands to add.
- `prosecutor`: builds the case for a verdict on a request under its disputed rules from a `detective` report, citing the Charter rule it rests on, the material evidence, and the precedents in `corpus/` that it applies or distinguishes, and the weaknesses of the case. Orchestrators run it after `detective`. If it asks for more evidence instead, they run `detective` on its requests, which adds to the report, and run `prosecutor` again, until it writes the case or they tell it that there will be no more evidence. They then run `oversight` on its case.
- `oversight`: checks that the evidence isn't fabricated: it verifies the facts of a `detective` report with `arbot` in whatever way it sees fit, and checks that each fact in the `prosecutor`'s case is one that `detective` collected, and each cited precedent against `corpus/`. Orchestrators run it on each case before `judge`. If it finds problems, they send its findings to `detective` if the report has any, then to `prosecutor`, which rebuilds the case on the corrected report, and run `oversight` again on the corrected case, and run `judge` only once it finds none.
- `judge`: reviews a `prosecutor`'s case only on its argument, under the disputed rules, against the full Charter and the past rulings the case cites, with its evidence taken as accurate, and accepts it or throws it out with the reasons. Orchestrators draft the ruling from an accepted case. If it throws the case out, they run `prosecutor` again with the judgment, which can ask `detective` for more evidence, and run `oversight` and `judge` on the new case. If no case is accepted within the rounds they allow, they give the Council the last case and judgment, marked as not accepted.

### Message board

`.msgboard/` is a scratch area where agents place files and communicate with each other, such as the fetched Charter and its summary. It is ignored by Git and never committed.

- Any agent may freely read and write files in `.msgboard/`, without asking for permission.
- The orchestrating agent defines the rules for each task: which files each sub-agent reads and writes, and how they are named. Sub-agents follow those rules and do not modify files they were not told to write.

## Development

Development commands are recipes in the [Justfile](./Justfile); run `just --list` to see them. Run `just precommit` before committing. It runs `just fix` to format the sources, then `just ci` to run all of the checks that CI runs.

- **End-to-end tests.** `internal/e2e` runs `arbot` against the deployed contracts' code on local [anvil](https://getfoundry.sh) nodes for Gnosis Chain and Ethereum Mainnet, with deterministic spoofed storage and WETH9 as the fee token. The Safe of the test transactions is a Safe 1.3.0 proxy on both nodes, which have the real Safe 1.3.0 and SafeL2 singletons, so tests can execute Safe transactions, and the Mainnet node keeps the states of its recent blocks so that `arbot classify` can read the Safe at `safeBlock`. They never use public RPCs. The tests are skipped when `anvil` is not installed, or with `go test -short`. Their artifacts are committed in `internal/e2e/testdata/anvil.json`. Regenerate them with `go generate ./internal/e2e` when the default addresses change; the tests fail with that hint if you forget.
- **Test data.** JSON files under `testdata/` must be formatted as `jq .` formats them, which `just check-testdata` checks.
