# Safenet Arbitration Bot

This bot helps the Safenet Security Council arbitrate disputed Safenet transactions. When sentinels split on a transaction, the `SentinelOracle` request is `FROZEN` and the Council must rule `secure` or `insecure` (or decide it is `out of scope`) under the Safenet Arbitration Charter, considering only the rules that the sentinels reported (see [Disputed rules](#disputed-rules)). The bot collects the evidence, runs deterministic Charter checks in code, falls back to an LLM for ambiguous cases, and drafts a ruling for humans to review. It also keeps a text corpus of past rulings that it uses as precedent.

> The repository is greenfield. This file describes the target architecture. Keep it up to date as components land, and replace "planned" wording with what actually exists.

## Protocol Background

### Sentinel oracle

- **Proposal.** A Safe transaction is proposed via `Consensus.proposeTransaction(oracle, oracleData, transaction)`. This emits `TransactionProposed(safeTxHash, safeId, oracle, epoch, oracleData, transaction)` and calls `SentinelOracle.postRequest`. The `transaction` is a `SafeTransaction` struct: `chainId, safe, to, value, data, operation, safeTxGas, baseGas, gasPrice, gasToken, refundReceiver, nonce`.
- **Request ID → transaction.** The oracle `requestId` is the Consensus `transactionProposal` message hash, `domainSeparator().transactionProposal(epoch, oracle, keccak256(oracleData), safeTxHash)`. `SentinelOracle` does not store the transaction. To find it, compute the proposal block as `getRequest(id).terms.commitDeadline - COMMIT_WINDOW`. Then take the `TransactionProposed` logs from `Consensus` in that block and pick the one whose recomputed message hash equals `requestId`.
- **Request lifecycle.** Sentinels bond and `commit`, then `reveal(requestId, approve, salt, reason)`. `finalize` settles the request:
  - a unanimous vote resolves it directly to `RESOLVED_APPROVED` or `RESOLVED_DENIED`;
  - no revealed votes time it out (`TIMED_OUT`, `RequestTimedOut`);
  - a split vote moves it to `FROZEN` and emits `DisputeTriggered(requestId, deadline)`. A dispute is only arbitrated in this `FROZEN` state.
- **Arbitration outcomes.** From `FROZEN`, the arbitrator (the Council's Arbitrator Safe) takes one of three paths:
  - `resolveDispute(requestId, approveWins, context)`, emitting `DisputeResolved(requestId, outcome, slashed, context)`. `approveWins = true` is a `secure` ruling and `false` is `insecure`. The losing side's sentinels are slashed.
  - `markOutOfScope(requestId, context)`, emitting `DisputeOutOfScope`.
  - No action. `timeoutArbitration` becomes callable after `deadline`, emitting `ArbitrationTimedOut`.

  Out of scope and timeout have the same economic effect: fees are refunded and bonds are returned in full. `context` is either the ruling text itself or an IPFS CID pointing to it.

- **Sentinel votes.** Each revealed vote carries a `reason` string that the protocol does not validate. By convention, `secure` votes have an empty reason and `insecure` votes cite the rules that the transaction fails, as a comma-separated list of rule identifiers such as `R-4.1, R-4.2` (§ 2.14). These reasons decide which rules a dispute is arbitrated under (see [Disputed rules](#disputed-rules)).
- **Two chains.** `Consensus` and `SentinelOracle` run on Gnosis Chain (chain ID 100). The disputed Safe can be on any network the Charter covers. Read the Safe's state (codehash, owners, modules, transfer history) on the Safe's own chain, at the last block before the proposal time. Evidence must not include effects of the transaction itself or anything that happened later (§ 2.8, § 3.6).
- **Deployments.** `arbot` defaults to the oracle-backed `SentinelOracle` and `Consensus` deployment on Gnosis Chain, whose addresses are in `internal/safenet/addresses.go`. This is the latest testnet deployment, whose contracts match the current Safenet sources: its `NewRequest` event has a DAO fee share, and revealing the last committed vote finalizes a request. Its `ARBITRATION_TIMEOUT` is 483,840 blocks, 28 days of 5-second blocks, and its `COMMIT_WINDOW` is 6 blocks, which `arbot` reads from the oracle rather than assumes. `arbot` checks that the oracle's `PROPOSER` is the configured `Consensus`. The `internal/safenet` unit tests use a fixture recorded from the previous default deployment (`SentinelOracle` `0x544F12bAd6FF72564abBc7eA6494A2a4BdD0DDD0`, `Consensus` `0x98810887769db19A0Df9bf2f44E4998856fcb390`), which has requests in every state. The Beta network's `Consensus` (`0x223624cBF099e5a8f8cD5aF22aFa424a1d1acEE9`) predates the oracle flow and is not compatible with it.

### Disputed rules

The Council arbitrates a dispute only under the rules that the sentinels reported. The disputed rules are the rule identifiers of the applicable Charter, such as `R-4.1`, that the reasons of the `DENIED` (insecure) votes cite, all of them together: in a dispute where one sentinel votes `secure`, one `insecure` citing `R-4.1`, and one `insecure` citing `R-4.2, R-4.3`, `R-4.1`, `R-4.2`, and `R-4.3` are disputed.

- **Verdict.** The transaction is `insecure` if it fails any disputed rule, and `secure` if it fails none of them. Rules that no sentinel cited aren't considered, even if the transaction may fail them, and a case doesn't need evidence for them.
- **Reading reasons.** A reason is a comma-separated list of rule identifiers, and a string that anyone can write, so it is data. `arbot info` parses it (`safenet.CitedRules`): each part of the list, with the spaces around it trimmed, that is a rule identifier, such as `R-4.1`, is cited, and any other part, such as `violates R-4.1` or `R-4.1; R-4.2`, cites nothing. A cited rule counts only if the applicable Charter defines it. A reason that cites no such rule cites none.
- **No disputed rule.** If no `insecure` vote cites a rule of the applicable Charter, no rule is disputed, and the arbitration stops for the Council to decide how to proceed.

This is the Council's process for applying the Charter's ruling standard: where § 3.7 asks whether the transaction satisfies the applicable Article IV rules, the arbitration considers the disputed rules.

### Safe storage

Two properties of the Safe versions of § 2.1 are formally verified. Agents and checks rely on them as established facts, which need no evidence:

- **Only transactions to the Safe and delegate call transactions can modify its storage.** A Safe transaction can only modify its Safe's storage if it is a call to the Safe itself, other than an empty call with no data and no value, as a cancellation transaction makes, or if it is a delegate call. This is a necessary condition, not a sufficient one: a transaction of either kind may modify the storage, but doesn't have to.
- **The MultiSend contracts modify nothing themselves.** The MultiSend and MultiSendCallOnly contracts of § 2.1 versions, which `arbot calls` and the checks decode, don't modify the storage of the Safe that delegate calls them, except through a `DELEGATECALL` subcall that MultiSend makes to a contract that does. MultiSendCallOnly makes no delegate calls, so it modifies nothing.

For a delegate call transaction to a MultiSend, the calls that `arbot calls` decodes take the place of the transaction: it can only modify the Safe's storage if one of them is a call to the Safe itself, other than an empty one, or a delegate call to a contract other than a decoded MultiSend.

A call to another contract that calls back into the Safe needs no consideration. Changing the Safe that way needs a separate authorization: for a Safenet-enabled Safe, a separate attestation, and a separate arbitration if it is disputed.

## Architecture

### Invariants

1. **The bot holds no keys and never writes onchain.** It only produces drafts. Humans on the Council review a draft and submit the ruling through the Arbitrator Safe.
2. **Deterministic rules live in Go code, not prompts.** A deterministic check judges one call that a Safe transaction makes, and finds it `insecure` with a rule citation, or `secure`, each with a short description, or it abstains. The relayer refund counts as a call. Passing one rule says nothing about the others (§ 3.7), so a check finds a call `secure` only for a class of calls that has no effect that any rule considers, whatever else the transaction does. For example, a delegate call to MultiSend with no transactions. A transaction is `secure` only if every call it makes is. A check that only shows that its own rule is not broken must abstain. Every other `secure` outcome comes from the LLM stage.
3. **LLM output is always a draft.** It must cite rules, name the precedents it applied or distinguished, and meet the ruling-explanation requirements of § 5.2: Safe and network, Charter version, rule IDs, material evidence, and the reason. Only admissible evidence may be used (§ 3.3–3.5).
4. **Sane defaults, no required configuration.** RPC URLs come from <https://chainlist.org/rpcs.json>. IPFS content (Charter versions, `context` CIDs) is fetched through public gateways. Overrides may exist, but no command may require them. Overrides go in an optional JSON configuration file, loaded by `internal/config` from `--config`, `./arbot.config.json`, or `$XDG_CONFIG_HOME/arbot/config.json`, in that order. A missing file means the defaults apply. Current settings are `rpcs` (chain ID to RPC URL, e.g. `{"1": "https://..."}`), `ipfs` (gateway base URL), `txServices` (chain ID to the base URL of the Safe Transaction Service, e.g. `{"1": "https://api.safe.global/tx-service/eth"}`, where an empty URL leaves the service out, and which defaults to Safe's public service for each network that the Charter covers), `sourcify` (the base URL of the Sourcify server, defaulting to Sourcify's public server, `https://sourcify.dev/server`), `oracle` and `consensus` (the Gnosis Chain `SentinelOracle` and `Consensus` addresses, defaulting to the deployments above), and `etherscan` (`{"apiKey": "...", "url": "..."}`, an Etherscan API key and the URL of Etherscan's multichain API, which takes the chain ID as its `chainid` query parameter, defaulting to its V2 API, `https://api.etherscan.io/v2/api`). Only the optional `arbot explorer` commands read `etherscan`, and they need its key, which has no default: without one, they fail with a message that says to configure `etherscan`, and their evidence is a gap ("Etherscan not configured"). The key is a secret, which no output, error, or URL that `arbot` reports contains.
5. **Go standard library only, as far as reasonably possible.** Do not add third-party modules for things the standard library makes easy to write. For example, write the Ethereum JSON-RPC client, ABI encoding and decoding, and IPFS/ENS lookups by hand on top of `net/http` and `encoding/json` rather than pulling in `go-ethereum`. A dependency is only justified for something that is impractical or risky to reimplement. Keccak-256 is one such case: the standard library's `crypto/sha3` does not provide it. Even then, prefer `golang.org/x/...` modules and keep them few. The JSON-RPC client is `internal/ethrpc`, whose `ScanLogs` splits `eth_getLogs` into block ranges that public RPCs accept, and whose `BlockTime` reads the timestamp of each block once, for the outputs that report the times of their blocks, in RFC 3339 UTC, such as `blockTime`, and fail if a read fails transiently (`ethrpc.Transient`), and ABI encoding and decoding is `internal/solabi`. The clients of public services (RPC nodes, IPFS gateways, the Safe Transaction Service, Sourcify, and the lists of RPCs and gateways) send their requests with `httpretry.Client`, which retries a request that is rate limited with `429 Too Many Requests`, or that a gateway rejects with `502 Bad Gateway`, `503 Service Unavailable`, or `504 Gateway Timeout`, with exponential backoff or after the response's `Retry-After`, up to 4 times. The clients only read, so a request can be sent again. Some nodes rate limit with a JSON-RPC error and HTTP status `200`, which `httpretry` doesn't see, so `ethrpc` retries the JSON-RPC rate limit codes (`-32005`, `-32016`, `-32029`) the same way. A request that still fails, such as for a rate limit, a server error, or a dropped connection, is a failure to get an answer, not an answer (`ethrpc.Transient`): code must never read it as "not found", "no trace", or "unknown", so commands fail on it, and `arbot` then says to run the command again later. `ScanLogs` doesn't shrink its block range on such a failure, since it isn't about the range.

### Components (planned)

- **`cmd/arbot`**: the single top-level Go CLI. Every capability lives here as a subcommand: fetching a request and its transaction, resolving the applicable Charter, reading a Safe's history, verifying that an account is an official Safe (codehash of a § 2.1 version at a given block), running deterministic checks, and indexing and linting the corpus. Put logic in `internal/` packages and keep `cmd/` thin. The subcommands live in `internal/cli`, and `cmd/arbot` only calls `cli.Run`, so the end-to-end tests run the CLI in-process and Go's test cache reruns them when it changes. Implemented so far:
  - `arbot charter [-block N | -request-file <path>] [-verify <file>]` resolves `charter.safenet-gov.eth` on Ethereum Mainnet and prints the Charter fetched from IPFS. With `-request-file`, it reads a request that `arbot info -json` wrote, and fetches the Charter that the request's `charter` name references at its `ethereumBlock`. With `-verify`, it doesn't fetch the Charter: it checks that the IPFS CID of the file is the one that the name references at the block, and prints the CID, or fails if they differ.
  - `arbot pending [-json]` lists the `FROZEN` requests awaiting arbitration as of the latest Gnosis Chain block, with their frozen block and deadline. It scans the last `ARBITRATION_TIMEOUT` blocks of oracle logs.
  - `arbot info [-json] <request-id>` shows a request, as of the latest Gnosis Chain block: its terms, its proposal and Safe transaction, the sentinel votes and reasons, the rules that each `DENIED` vote's reason cites and all of them together, the [disputed rules](#disputed-rules), and its arbitration, if any. With `-json`, each vote has its `rules`, empty for a vote that isn't `DENIED`, and the request has its `disputedRules`, in the order of their first citation. The rules are parsed from the reasons alone, so some may not be rules that the applicable Charter defines. The proposal includes the last blocks before its time on Ethereum Mainnet and on the Safe's chain (`ethereumBlock` and `safeBlock`), found with `ethrpc`'s `SearchBlock`, and their timestamps (`ethereumBlockTime` and `safeBlockTime`), which a request file written before arbot reported them lacks. Read the Safe's state at `safeBlock`, and fetch the Charter with `arbot charter -request-file`. A request of the oracle has no `vector` field, which only a request that `arbot vector` makes has.
  - `arbot classify [-json] <request-id>` runs the deterministic checks on a request and prints its verdict: `unclassified`, or the classification that decided it, `secure  <description>`, or `insecure  <rule>  <description>`. A `secure` description joins those of the checks that matched each call with `; `. With `-json`, it writes `{"verdict": null | "secure" | "insecure", "rule": "...", "description": "..."}`, leaving out an empty rule or description. With `-request-file <path>` in place of the request ID, it classifies the request that `arbot info -json` wrote to the file, without fetching it, though the checks still read the Safe's chain. With `-list` in place of the request ID, it lists the classification of every check, in the order that they run, as a table with a verdict, rule (`-` if none), and description column, or with `-json`, as an array of classifications.
  - `arbot calls [-json] [-abi] -request-file <path>` lists the calls that the Safe of a request that `arbot info -json` wrote makes, as `arbot classify` judges them, read from the Safe's chain as of its `safeBlock`: delegate calls to the MultiSend and MultiSendCallOnly contracts of § 2.1 versions decoded into the calls that they make, a root call that reverts whatever the state or makes no calls replaced by a `reverting` or `empty` placeholder, and a last `refund` call that pays the largest gas refund that the transaction allows, if any. It shows the Safe's code hash and the § 2.1 proxy version whose official proxy factory deploys a proxy with that code on its network, and its singleton, in storage slot 0, with its § 2.1 singleton version, each if any. Each account that the Safe calls has its code hash and size, whether it is the Safe itself, and the contract of a § 2.1 version that it is (MultiSend, MultiSendCallOnly, CreateCall, or the Safe or SafeL2 singleton), identified by its address on the networks that the Charter covers if it has code, and for CreateCall, by its code hash too, as safe-deployments lists them. Each call's data is decoded as a well-known function, if it is one (`internal/functions`): ERC-20 `transfer`, `transferFrom`, and `approve`, the Safe's `execTransaction`, whose `data` is decoded the same way, as the call that the Safe makes, the Safe proxy factories' `createProxyWithNonce`, and CreateCall's `performCreate` and `performCreate2`. Data is decoded by its selector and ABI layout only, so what a call does depends on the account that it is to. A call to a CreateCall of a § 2.1 version, of 1.3.0 (both of its deployments), 1.4.1, or 1.5.0, has the address of the contract that it would deploy, derived from its data (`internal/create`), which is arithmetic over onchain data, not a deployment that the chain shows: the deployer is the CreateCall for a call and the Safe for a delegate call, a `performCreate2` address is `keccak256(0xff ++ deployer ++ salt ++ keccak256(initCode))[12:]`, and a `performCreate` address is `keccak256(rlp([deployer, nonce]))[12:]`, with the deployer's nonce at `safeBlock` (`eth_getTransactionCount`) plus one for each deployment by the same deployer that an earlier call to a CreateCall in the transaction makes, CREATE2 included, since both increment it. A deployment that another call makes, such as one by a contract that the Safe delegate calls, isn't counted, and the nonce is only right if the transaction runs on the state at `safeBlock`. A failed deployment reverts the call, so nothing is deployed there. With `-abi`, each call whose data has a selector but isn't a well-known function is also decoded with the ABI that Sourcify verified for the account that it calls (an offchain source, § 3.4, `simulate.ABIDecoder`), with the arguments decoded as `arbot simulate` decodes them, looking up each account once: a call to an unverified account isn't decoded, and says so. Without `-abi`, Sourcify isn't asked. It prints the Safe, the target of the Safe transaction's own call, and a table of the calls with their functions, such as `execTransaction > transfer`, or with `-abi`, `deploy(bytes,bool) (sourcify)` or `- (unverified)`, and long data shortened, then the derived addresses of the contracts that the calls create, with their inputs, or with `-json`, `{"chainId", "safeBlock", "safe": {"address", "codeHash", "codeSize", "proxyVersion", "singleton", "singletonVersion"}, "target": <account>, "calls": [{"kind": "root" | "batched" | "refund", "placeholder", "to": <account>, "value", "operation", "data", "function", "creates", "abi"}]}`, where an account is `{"address", "codeHash", "codeSize", "self", "contract": null | {"name", "version"}}`, the versions are null if there is none, `placeholder` is left out of a call that isn't one, `function` is null or `{"name", "signature", "args": [{"name", "type", "value", "call"}]}`, where `call` is the decoded function of a `bytes` argument that is the data of a call, left out if it isn't one or isn't decoded, `creates` is `{"source": "derived", "address", "method": "create" | "create2", "deployer", "salt" | "nonce", "initCodeHash"}`, left out of a call that isn't to a CreateCall or whose data doesn't decode, and `abi` is `{"status": "verified" | "unverified" | "no-code", "source": "sourcify", "url", "observedAt", "function": null | {"signature", "inputs": null | [{"name", "type", "value"}]}}`, left out without `-abi` and of a call that it doesn't look up, where `url` and `observedAt` are left out for an account without code, `function` is null if the account isn't verified or its ABI has no function with the selector, and `inputs` is null as in `arbot simulate`. The logic is `checks.Calls`, which shares the decoding of the checks.
  - `arbot account [-json] [-block N] [-spender <address>] -request-file <path> <address>` shows an account on the Safe's chain of a request that `arbot info -json` wrote, as of its `safeBlock`, or the earlier block `-block`, which can't be after it, such as a recipient or a token: its code hash and size, whether it is the Safe itself, and the contract of a § 2.1 version that it is, as `arbot calls` shows the accounts that a Safe calls, its balance of the native currency in wei, and its nonce. If it answers `decimals()` and `balanceOf(address)` as an ERC-20 token does, it also shows the name, symbol, decimals, and total supply that it returns, which are what the contract claims, not what it is, and the Safe's balance of it, and with `-spender`, the Safe's allowance of it to the spender (`erc20.Read` and `erc20.Allowance`). An account whose calls revert, or return data that isn't an answer, isn't a token, but a request to the node that fails rather than being answered fails the command (`ethrpc.Transient`), even if its error names a revert, since it says nothing about the account.   - `arbot safe [-json] [-address <address>] [-at N] [-compare <address>] -request-file <path>` shows the settings of the Safe of a request that `arbot info -json` wrote, as § 2.10 lists them, read from the Safe's storage on its chain as of its `safeBlock` with the storage layout of the § 2.1 Safe versions (`internal/safesettings`), rather than by calling the singleton's code: its singleton, owners, threshold, nonce, enabled modules, fallback handler, guard, and module guard, which only Safe 1.5.0 has. Only an account that `arbot calls` would identify as a Safe of a § 2.1 version has settings: one whose code is that of a SafeProxy of a § 2.1 proxy version on its network, and whose singleton, in storage slot 0, is a Safe or SafeL2 singleton of a § 2.1 version. The storage of any other account isn't read as settings, since zeros would read as a Safe without owners. The zero address means that a setting isn't set. It fails if a list of owners or modules doesn't end where it started, and if a request to the node fails rather than being answered (`ethrpc.Transient`). Without flags, it prints the settings and the lists, or with `-json`, `{"safe", "chainId", "safeBlock", "singleton", "owners", "ownerCount", "threshold", "nonce", "modules", "fallbackHandler", "guard", "moduleGuard"}`, where the lists are in the order that the Safe links them, and `ownerCount` is the count that the Safe stores apart from its list, and it fails if the Safe isn't a Safe of a § 2.1 version, with the reason. With `-address`, it shows the settings of another account on the Safe's chain instead, such as a recipient or a nested Safe, and with `-at`, it reads them as of an earlier block, which can't be after `safeBlock`. Either way, its JSON is `{"chainId", "safeBlock", "address", "codeHash", "codeSize", "proxyVersion", "singleton", "singletonVersion", "block", "settings": null | {"singleton", "owners", "ownerCount", "threshold", "nonce", "modules", "fallbackHandler", "guard", "moduleGuard"}, "reason"}`, with the identification of `arbot calls -json`'s `safe`, the block that it read, and the settings, or null and a `reason` that is `no-code`, `not-a-safe-proxy` (its code isn't a § 2.1 SafeProxy on its network), or `unknown-singleton` (its singleton isn't a § 2.1 singleton, so its storage layout is unknown), which is left out if it has settings. With `-compare`, it compares the settings of two accounts, A and B, field by field from storage: A is the Safe, or `-address`, and B is the `-compare` account, both as of `safeBlock`, or with `-at`, A is the `-compare` account at `-at` and B the same account at `safeBlock`, which `-address` doesn't apply with. It prints both accounts, a table of each setting with `equal` or `different` and both values, the owners and modules that both have and those that only one has, and whether every setting but the nonce is the same, or with `-json`, `{"chainId", "safeBlock", "a": <account>, "b": <account>, "diff": null | {"singleton", "owners": <list>, "ownerCount", "threshold", "nonce", "modules": <list>, "fallbackHandler", "guard", "moduleGuard", "sameConfiguration"}}`, where an account is as `-address -json` has it without `chainId` and `safeBlock`, each setting is `"equal"` or `"different"`, a list is `{"result": "equal" | "different", "shared", "onlyA", "onlyB"}`, compared as sets, since the order of a list is only the order that its entries were added in, with `shared` and `onlyA` in A's order and `onlyB` in B's, `sameConfiguration` is whether every setting but the nonce is equal, and `diff` is null unless both accounts have settings. Shared owners or an identical configuration are facts about who controls two Safes, not by themselves evidence that a recipient is inside the expected target set (§ 2.4): the ruling on `0x8b83aa12d81c160fc8f1b2dd5af6e4f8032e61a6b648ff9e2cdb80f6570c3b2d` gave a recipient's owners, which matched the Safe's, no weight, and the text output says so. A non-standard singleton's storage layout isn't decoded. The logic is `safesettings.ReadAccount` and `safesettings.Compare`.
  - `arbot contract-source [-json] [-file <file>] -request-file <path> <address>` prints the source files of the contract at an address on the Safe's chain of a request that `arbot info -json` wrote, which Sourcify verified by compiling them into the contract's code, or with `-file`, only the file with that path in the compilation, such as `contracts/Safe.sol`. Like `arbot signatures`, it reports Sourcify's record of the contract (`sourcify.Fetch`), fails unless the code that Sourcify verified is the account's code as of `safeBlock`, and only has the proxy's own sources for a proxy. The text output prints the record, then each file after a `==> <path> <==` line, with the characters that a terminal doesn't print, such as escape sequences and bidirectional text controls, escaped as in a Go string. With `-json`, it writes `{"chainId", "safeBlock", "address", "codeHash", "codeSize", "status", "source", "files": [{"path", "content"}]}`, with the status and source of `arbot signatures`, and the files as they are, in the order of their paths, null for an `unverified` contract and empty for an account with `no-code`.
  - `arbot signatures [-json] -request-file <path> <address>` lists the functions of the contract at an address on the Safe's chain of a request that `arbot info -json` wrote, with their signatures, selectors, and state mutability, and whether it has a fallback or receive function, from the contract's ABI that Sourcify verified (`internal/signatures`, `internal/sourcify`). Sourcify is an offchain source (§ 3.4), so it reports the URL that it fetched the ABI from and when, how well Sourcify's compilation matched the code, and the contract's fully qualified name and compiler version. It fails unless the code that Sourcify verified is the account's code as of `safeBlock`. In a contract compiled from Solidity, a call whose data starts with no function's selector runs the fallback function, and one with no data runs the receive function, or else the fallback function, and reverts without it. A proxy's ABI has only the proxy's own functions, so its implementation, such as a Safe's singleton, needs a lookup of its own. It prints the contract, its code, the source, and a table of selector, signature, and state mutability, or with `-json`, `{"chainId", "safeBlock", "address", "codeHash", "codeSize", "status": "verified" | "unverified" | "no-code", "source": null | {"name", "url", "observedAt", "match", "runtimeMatch", "verifiedAt", "contract", "compiler"}, "functions": [{"selector", "signature", "stateMutability"}], "fallback": null | {"stateMutability"}, "receive": null | {"stateMutability"}}`, where the functions of an `unverified` contract are null, since they are unknown, those of an account with `no-code` are empty, and so is its source, which has only its name, URL, and observation time for an `unverified` contract.
  - `arbot transfers [-json] [-in] [-from <address>] [-to <address>] [-blocks N | -all] -request-file <path>` lists the ERC-20 transfers out of the Safe of a request that `arbot info -json` wrote, read from the Safe's chain as of its `safeBlock`: the `Transfer` events of any token that has the Safe as sender, in the last `-blocks` blocks up to `safeBlock` (default 100,000), or only those to `-to`. It scans that range only, and reports it, so a transfer before it isn't listed. It checks that every address (40 hex digits), hash (64), and other hex value of at least 8 digits, such as a selector or data, is in a source, whole or as part of a longer value, ignoring case; that every abbreviation with `…` or `...`, such as `0x1235…4306` or `0xce3b5448…`, shortens a value of a source: one that starts and ends with its digits, an address or 32-byte word in other data that does, data that has its digits for one without an end, or a source's own abbreviation of it; that every number of 4 or more digits before any decimal point, with or without thousands separators, such as `87,777`, is a number of a source, however that formats it, other than digits in a word, such as `ERC-20`, a version, such as `1.4.1`, or a date; that every RFC 3339 time is in a source; that every blockquote after the first `##` heading, which the template's notice comes before, and outside code blocks, is in `charter.md` verbatim, ignoring Markdown blockquote, list, and heading markers and whitespace, with each part around a `…` in it; and that every request ID or abbreviation of one in the Precedents section, in a `precedents:` tag, or followed by a parenthesis that starts with an outcome, such as `(insecure)`, which applies to each request ID between it and the parenthesis before it, is a ruling of the corpus other than the request's own, with that outcome. An abbreviation in the Precedents section that matches no ruling, and has no outcome, may be an address of a source instead. A number that no source has is a warning, not an error, if the report marks it as derived, with `about`, `approximately`, `roughly`, `around`, `nearly`, `almost`, `~`, or `≈` right before it, or `derived` on its line, and so are a quotation each of whose lines is in the Charter, but not together, and an abbreviation that matches several rulings. If the directory has `evidence-summary.json`, it also checks that it has the fields that the `evidence` skill defines and no others, that a fact's source is `onchain` with a command and a block, `offchain` with a command, URL, and observation time, or `derived` from other facts, that the uncertainty is `low`, `medium`, or `high`, that the suggested ruling is marked as a suggestion, that `humanReview` is `true`, with reasons, if the uncertainty is `high` or a gap is `decisive`, and that the report of a summary with `humanReview` says "Human review: required". With `-file`, it checks another file of the directory instead, such as `case-<n>.md` for `oversight`, against the same sources without the cases and judgments, since a case must only state facts that the evidence has. It checks that a value is in a source, not that it is the right value in its place: a block that a source has for another event passes. It prints each error, then each warning, as `<file>:<line>: error|warning: <kind> <value>: <message>`, then the counts and the sources, or with `-json`, `{"errors": [<finding>], "warnings": [<finding>], "sources": [...], "rulings": [...]}`, where a finding is `{"file", "line", "kind": "address" | "hash" | "hex" | "abbreviation" | "number" | "time" | "quotation" | "precedent" | "outcome" | "summary", "value", "message"}`, `line` is 0 for a finding on a file as a whole, `sources` are the names of the files of the directory that it read, and `rulings` are the paths of the corpus files of the rulings that the file names. It exits with status 1 if there are errors. It replaces an ad-hoc script that checked only hashes and addresses, after a wrong Safe transaction hash and a wrong data length slipped into two drafts.
  - `arbot index [-w] [-corpus <dir>] [-block N]` indexes the arbitrator's rulings into the [rulings corpus](#rulings-corpus) in `<dir>` (default `corpus`): the requests with a `DisputeResolved` or `DisputeOutOfScope` event of the oracle after the block in the corpus's `index.json`, up to `-block` (default: the latest finalized Gnosis Chain block). It writes a corpus file for each, and moves the index to `-block`. It reads the requests as of the latest block, which gives the same requests as reading them at `-block`, since a ruling settles a request for good, so its output depends only on the blocks up to `-block` and the corpus. Without `-w`, it prints the corpus files and the index that it would write, each after a `==> <path> <==` line. With `-w`, it writes them, the index last. It keeps a corpus file that already exists with the same content, and fails if one exists with other content, before it writes anything.
  - `arbot tags [-json] [-corpus <dir>] <request-id>` lists the tags of the ruling on a request in the corpus in `<dir>` (default `corpus`): the `key: value` lines of the file's header, then, after an empty line, those of the header that its ruling document starts with, if it has one (see [Rulings Corpus](#rulings-corpus)). With `-json`, it writes `{"header": {...}, "document": {...}}`, each an object of tags by key.
  - `arbot vector [-json] <spec.json>` makes a request of a [Sentinel test vector](https://github.com/safe-research/sentinel-test-vectors), from its spec file, so that the commands that take `-request-file` and `arbot classify -request-file` run on it, as they run on a request that `arbot info -json` wrote (`internal/vector`). A vector is a Safe transaction (`request.transaction`), the block of its chain to judge it at (`request.block`), the verdict and rule that a correct sentinel answers (`response`), and notes (`metadata`). The request has the vector's transaction, its block as `safeBlock`, the transaction's Safe transaction hash, and, as its `disputedRules`, the vector's rule for an `insecure` vector, and none for a `secure` one. It has no oracle request behind it, so it has no oracle fields: its `id`, `oracle`, `charter`, terms, fee, proposal block and time, and `txHash` are zero or empty, its `votes` empty, its `arbitration` null, and its `ethereumBlock` 0, and it has no block times. The commands that read the oracle or the Charter that a request names, `arbot status` and `arbot charter -request-file`, don't apply to it. It is marked as a vector with `"vector": {"path", "verdict", "rule", "eoa"}`: the spec file's path as given, the vector's verdict and rule (`""` for a secure vector), and whether its note starts with "EOA transaction.", for a vector that the vectors' README says is recast from a transaction of an externally owned account, with the account as the `safe`. No Safe exists at an EOA vector's Safe address, so `arbot classify` finds it insecure under R-4.0, and `arbot safe` and `arbot executions -all` fail on it, which says nothing about the rule that the vector asks about. It prints the vector, its Safe transaction, and its disputed rules, or with `-json`, the request, which is the request file to pass to `-request-file`, such as `arbot vector -json spec.json > request.json`. It fails for a spec that doesn't match the vectors' `schema.json` in the fields that a request needs, or that has a field that it doesn't define.

  Flags must come before a request ID.

- **Deterministic checks**: one Go check per class of calls that the Charter decides, each with its verdict, the rule ID for `insecure`, and a short description. Checks live in `internal/checks` and are listed in its `checks` variable, grouped by verdict in the order that they run. A check judges one call at a time, given the Safe's address and chain ID, and an `env` from which it can read the Safe's chain at `safeBlock`. The calls are those that the Safe makes, with delegate calls to the MultiSend and MultiSendCallOnly contracts of § 2.1 versions decoded into the calls that they make, followed by a synthetic call that pays the largest relayer refund the transaction allows. Each call's `kind` is `Root`, `Batched`, or `Refund`, for the Safe transaction's own call, a call of a MultiSend, and the refund. A call that reverts whatever the state, such as a call to MultiSend that isn't a delegate call, is replaced by a placeholder from `revertingMultiSend`: a call with no data to the MultiSend that the Safe transaction calls. The transaction still pays its refund after a reverting call. A MultiSend that makes no calls is replaced by one from `emptyMultiSend`: a delegate call to its `multiSend` with no transactions. A transaction therefore always makes at least one call. There are no `out-of-scope` checks: R-4.0 applies to every transaction, on any network, so every transaction is in the scope of Article I (§ 3.9). `arbot classify` runs the `insecure` checks on every call: first `offNetwork` for a Safe on a network that Article I doesn't list, and `unsupportedSafe` for an account that isn't a Safe under § 2.1, both under R-4.0, then others such as one for each Safe function that changes a setting under R-4.1. It returns the classification of the first check that matches a call. Otherwise, the request is `secure` if a `secure` check matches every call, and `unclassified` if not. `arbot classify -list` lists the checks. `arbot classify` runs every check, whatever the [disputed rules](#disputed-rules) are, so the `arbitrate` skill uses an `insecure` classification only if its rule is disputed, and a `secure` one, which holds under every rule, as it is. Add a check only for cases the Charter makes unambiguous. For example, R-4.1 makes a settings change such as `addOwnerWithThreshold` insecure unless it matches an allowed exception. Use the `add-check` skill (`skills/add-check/SKILL.md`) to add one.
- **Agent layer**: `claude` and `codex` for now. Agents get their data by shelling out to `arbot`. The facts that `arbot` reports are correct, including the identifications that it makes, such as the § 2.1 proxy and singleton versions of a Safe that `arbot calls` reports, which it makes by verifying the Safe's code hash and singleton address against the official deployments of that version on the Safe's network. Agents take them as established, and don't ask how `arbot` made them, read its source code to explain them, or record its internals as gaps: a wrong fact is a bug in `arbot`, to fix in `arbot`, not a question for an arbitration. They must not reimplement chain reads or checks in ad-hoc scripts, such as with `cast` or `curl`. When `arbot` can't provide some evidence, they report it as a gap, and the `add-evidence` skill adds the command that provides it, so that an arbitration can be done with `arbot` alone. Agent skills live in `skills/<name>/SKILL.md`, with `.claude/skills` and `.codex/skills` symlinked to that directory. The `add-check` skill adds a deterministic check, `add-evidence` adds an `arbot` command that gathers evidence, and the playbooks that use it, `add-subagent` adds a sub-agent, `evidence` collects the evidence for a request, and `arbitrate` drafts a ruling for a request under its [disputed rules](#disputed-rules): it reads the proposal's status with `arbot status`, classifies the request with `arbot classify`, and if the checks don't decide the disputed rules, runs the sub-agents to build and review a case under them, then fills in the template `skills/arbitrate/report.md` in `.msgboard/<first 12 characters of the request ID>/` itself, and checks its values with `arbot check-report`. The `evidence` skill (`skills/evidence/SKILL.md`) has the rules for running `arbot`, which the orchestrator gives every sub-agent: run commands one at a time, since public RPCs rate limit; read a command that fails because a request to a node failed as a failure, never as an answer, and run it again later, or with another RPC URL; name tokens only as `arbot` reports them; never decode calldata or compute addresses by hand; and use the whole-history commands, `arbot executions -all` and `arbot transfers -all`. Its playbooks, next to it, give the `arbot` commands to run, in order, for each kind of case, what each output shows and can't show, the Charter references of its facts, and the known gaps: `proposal-status` for every case, `value-recipient` for R-4.3, `approval-spender` for R-4.4 and R-4.5, `settings-and-delegatecall` for R-4.0 to R-4.2, and `target-risk` for R-4.6, whose known gaps include that public security flags (§ 2.7) aren't checked, since no trusted provider is integrated, which the Council checks by hand. Their `arbot explorer` steps are optional: they run only if an Etherscan API key is configured, and without one, their evidence is recorded as a gap, "Etherscan not configured". It ends with an evidence summary, `evidence-summary.json` and `.md`: the facts, each with its source (`onchain`, `offchain` with its URL and observation time, or `derived`), its block and time, and the rules it bears on, the gaps, the conflicts between sources, the uncertainty, a suggested ruling, which is a suggestion for the `prosecutor` and the `judge`, not a verdict, and `humanReview`, which is `true` when the uncertainty is high or a decisive gap is open. A test checks that every `arbot` command and flag that the skills, the agents, and this file mention exists. Sub-agents are described under [Agents](#agents).
- **Future direction**: using a general-purpose coding agent is a stopgap. The plan is to move to a purpose-built arbitration agent (for example, on Google's ADK) with a narrow toolset backed by the same `arbot` commands. Build tooling so that move is easy: stable CLI output (JSON where machines consume it) and no dependence on one agent's quirks.

### GitHub workflows

- **Arbitrate** (planned, `workflow_dispatch`, input `request_id`): fetches the request, then runs the deterministic checks. If a check fails, it drafts the ruling from that failure. Otherwise it runs the agent with the relevant corpus precedents. It then opens an issue with the classification and the draft ruling for Council review.
- **Index** (`.github/workflows/index.yml`, hourly `cron` and `workflow_dispatch`): runs `arbot index -w`, and on `main`, commits the new corpus files and index and pushes them, with the `CORPUS_BOT_SSH_KEY` deploy key of the `corpus-index-main` environment. On other branches, it indexes without committing, to test the workflow.
- **Configure** (`.github/actions/configure`): a composite action for workflows that run `arbot`. It writes a configuration file with the RPC URLs of Ethereum Mainnet (an archive node), Gnosis Chain, and Arbitrum One, and the IPFS gateway URL, that it is given, leaving out those that are empty, and outputs its path for `arbot -config`. Workflows pass it the `MAINNET_RPC_URL`, `GNOSIS_RPC_URL`, `ARBITRUM_RPC_URL`, and `IPFS_GATEWAY_URL` secrets, since public RPCs and gateways rate limit runs, and work without them.

## Rulings Corpus

`corpus/` holds one Markdown file per onchain-recorded arbitration outcome, named `corpus/<requestId>.md`. Every file starts with a header that has **exactly 10 lines**. Agents can therefore scan all past cases with `head -n 10 corpus/*.md`, list the tags of a case with `arbot tags <request-id>`, and then read in full only the cases that look relevant.

```
---
request: 0x<requestId>
outcome: secure | insecure | out-of-scope
rules: R-4.1, R-4.5            (or -)
chain: <Safe chain ID>
safe: 0x<Safe address>
charter: <IPFS CID of applicable Charter version>
proposed: <ISO-8601 UTC proposal time>
record: 0x<Gnosis Chain tx hash of resolveDispute/markOutOfScope>
---
```

Rules for the header:

- Every key is always present, in this order, on a single line. Use `-` when a field is empty.
- Headers are generated by `arbot index`, not written by hand. It fills in `rules` with the rule IDs, such as `R-4.1`, that the ruling document cites, in the order they are first cited.
- If the header format changes, change the line count here, in the tool, and in the skills and agents together.

The body follows the header: the proposal, the decoded Safe transaction, the sentinel votes and reasons, and the ruling. Then a `<!-- DOCUMENT START -->` line and a `---` line, followed by an empty line, start the ruling document: the IPFS document that the ruling's `context` references, or the `context` itself if it is the ruling text. Everything after them is the document, verbatim. Prettier ignores `corpus/`, since its files must stay as `arbot index` writes them.

The ruling document may start with a header of its own, delimited by `---` lines like the file's header, with one `key: value` tag per line, such as:

```
---
precedents: <comma-separated request IDs applied or distinguished, or ->
tags: <comma-separated kebab-case fact-pattern keywords>
summary: <one line describing the fact pattern and holding>
---
```

The Council writes these tags in the ruling, so they are only as accurate as the ruling. `arbot tags` lists them after the file's header tags. A document whose header is malformed, such as one with a YAML list, has no tags.

`corpus/index.json` is `{"block": N}`, where `N` is the last Gnosis Chain block whose rulings are in the corpus. The corpus starts at the block of Wednesday, October 14, 2026, 00:00:00 UTC (48,743,477), so the empty corpus has the block before it.

## Sub-agents

Each sub-agent's instructions live in `agents/<name>.md`, shared by both CLIs. Stubs in `.claude/agents/<name>.md` and `.codex/agents/<name>.toml` register them with Claude Code and Codex CLI, set the model, and point to the shared instructions. Use the `add-subagent` skill (`skills/add-subagent/SKILL.md`) to add or change one.

- `charter-summarizer`: summarizes a fetched Charter, preserving rule identifiers, exceptions, and section citations.
- `detective`: collects the evidence for a request with `arbot` commands, for its disputed rules, following the playbooks of the `evidence` skill, given the request that `arbot info -json` wrote, its status and classification, the disputed rules, and the Charter summary, and writes a report of the facts, each with its source and the rules it bears on, and of the gaps that `arbot` can't fill yet, and the evidence summary. It only collects evidence, and leaves the verdict to `prosecutor`. Orchestrators run it after `charter-summarizer` for a request that `arbot classify` leaves `unclassified`, before drafting a ruling, and use its gaps to decide which `arbot` commands to add.
- `prosecutor`: builds the case for a verdict on a request under its disputed rules from a `detective` report and its evidence summary, citing the Charter rule it rests on, the material evidence, and the precedents in `corpus/` that it applies or distinguishes, and the weaknesses of the case. Orchestrators run it after `detective`. If it asks for more evidence instead, they run `detective` on its requests, which adds to the report, and run `prosecutor` again, until it writes the case or they tell it that there will be no more evidence. They then run `oversight` on its case.
- `oversight`: checks that the evidence isn't fabricated: it verifies the facts of a `detective` report and its evidence summary with `arbot` in whatever way it sees fit, and checks that each fact in the `prosecutor`'s case is one that `detective` collected, its values with `arbot check-report -file`, and each cited precedent against `corpus/`. Orchestrators run it on each case before `judge`. If it finds problems, they send its findings to `detective` if the report has any, then to `prosecutor`, which rebuilds the case on the corrected report, and run `oversight` again on the corrected case, and run `judge` only once it finds none.
- `judge`: reviews a `prosecutor`'s case only on its argument, under the disputed rules, against the full Charter and the past rulings the case cites, with its evidence taken as accurate, and accepts it or throws it out with the reasons. Orchestrators draft the ruling from an accepted case. If it throws the case out, they run `prosecutor` again with the judgment, which can ask `detective` for more evidence, and run `oversight` and `judge` on the new case. If no case is accepted within the rounds they allow, they give the Council the last case and judgment, marked as not accepted.

### Message board

`.msgboard/` is a scratch area where agents place files and communicate with each other, such as the fetched Charter and its summary. It is ignored by Git and never committed.

- Any agent may freely read and write files in `.msgboard/`, without asking for permission.
- The orchestrating agent defines the rules for each task: which files each sub-agent reads and writes, and how they are named. Sub-agents follow those rules and do not modify files they were not told to write.

## Development

Development commands are recipes in the [Justfile](./Justfile); run `just --list` to see them. Run `just precommit` before committing. It runs `just fix` to format the sources, then `just ci` to run all of the checks that CI runs.

- **End-to-end tests.** `internal/e2e` runs `arbot` against the deployed contracts' code on local [anvil](https://getfoundry.sh) nodes for Gnosis Chain and Ethereum Mainnet, with deterministic spoofed storage and WETH9 as the fee token. The Safe of the test transactions is a Safe 1.3.0 proxy on both nodes, which have the real Safe 1.3.0 and SafeL2 singletons, so tests can execute Safe transactions, and the Mainnet node keeps the states of its recent blocks so that `arbot classify` can read the Safe at `safeBlock`. They never use public RPCs. The tests are skipped when `anvil` is not installed, or with `go test -short`. Their artifacts are committed in `internal/e2e/testdata/anvil.json`. Regenerate them with `go generate ./internal/e2e` when the default addresses change; the tests fail with that hint if you forget.
- **Test data.** JSON files under `testdata/` must be formatted as `jq .` formats them, which `just check-testdata` checks.
- **Fixture tests of past arbitrations.** `internal/replay` serves recorded JSON-RPC exchanges by chain and recorded HTTP replies of services, such as the Safe Transaction Service and Sourcify, by path and query, so that tests run arbot's commands on what the chains and services answered once, without the network; a request that wasn't recorded fails the test. With `-record`, it records them instead, from live nodes and services, keeping only the fields that arbot reads (`replay.Trim`) and no URL, so that a fixture has no key that an RPC URL may carry. The `TestCase*` tests of `internal/cli` run the commands of the evidence playbooks on the requests of past rulings in `internal/cli/testdata/cases`, and pin the facts that the rulings rested on, and `internal/status`'s `TestFixtures` uses the same fixtures. Record them again with `go test ./internal/cli -run TestCase -record -record-config <config>`, with a configuration file whose Ethereum Mainnet RPC URL is an archive node.
- **Sentinel test vectors.** `just vectors [dir] [flags]` runs `internal/cmd/vectors` on the vectors of <https://github.com/safe-research/sentinel-test-vectors> cloned in `dir` (default `../sentinel-test-vectors`): for each vector, `arbot vector`, `arbot classify -json -request-file`, and the commands of the evidence playbooks that match its rule, or of every playbook for a secure vector, which it reads from their Markdown (`internal/playbooks`), so that they can't drift from what the agents run. It writes a Markdown and a JSON report, `vectors.md` and `vectors.json` in `-out` (default `.msgboard/vectors`), with each vector's expected verdict and rule, the deterministic result and how it compares (`internal/vector`), and the commands that failed, and a summary, in which no vector may be decided wrongly. It skips the optional `arbot explorer` commands unless the configuration has an Etherscan API key, so that a run without one doesn't fail on them. It runs one command at a time, and runs a command again after a wait if a request to a node or a service failed. With `-run <regexp> -keep`, it runs only the matching vectors, such as those that a rate limit failed, and keeps the other vectors' results from the report in `-out`. It reads chains at old blocks, so it needs an archive node, such as with `-config <file>`, and isn't part of CI. Run it after adding a deterministic check, after changing a playbook, and when vectors are added. [`docs/evidence-skills.md`](docs/evidence-skills.md) documents the evidence commands and playbooks, how to validate them, and the manual steps that they save.
